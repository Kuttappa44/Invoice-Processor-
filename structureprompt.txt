Project structure prompt
Build this as a multi-package application. Never put the product into one or two files. A new capability gets a new folder. A folder that starts mixing unrelated jobs gets split before it grows.

Repository

      config.py               # settings, one place

backend/ and frontend/ are separate apps. They share a contract (request and response shapes), not source files.

Backend rules
main.py creates the app, registers middleware, and mounts routers. It contains no business rules and no SQL.

Every product module lives at app/modules/<name>/ and uses this layout. Omit a file only when that role does not exist yet. Do not merge roles to save files.

modules/<name>/
  router.py          # HTTP only
  schemas.py         # request and response models
  service.py         # business rules and transactions
  models.py          # persistence models
  workers/tasks.py   # background jobs for this module
When a module grows, add a subpackage by responsibility (matchers/, extractors/, pdf.py). Do not add a second copy of service.py named service2.py, and do not keep appending to the same file once it handles two different jobs.

Layer rules:

router.py validates input, checks permission, calls one service function, and returns a schema. No queries, no branching business rules, no calls to third-party APIs.
schemas.py is the API contract. Do not return raw database rows from a route.
service.py owns the use case: load data, apply rules, write, commit. Other modules call a service function, not another module's router or tables.
models.py is storage shape only. No HTTP and no formatting for the UI.
workers/tasks.py is for anything slow or retryable (mail, sync, file processing). The route enqueues the job and returns. The worker calls the same service functions the route would.
shared/ is for stateless helpers needed by two or more modules (pagination, money, mail transport). If only one module uses it, it stays inside that module.
core/ is identity, accounts, and permissions. Product features do not go here.
integrations/ has a small interface (base.py), a registry, and one file per provider. The provider-specific client is the only code that knows that provider's payload shape. Mapping, polling, and retries stay outside the client file.
config.py is the only reader of environment variables. Other modules receive settings or function arguments.
scripts/ are one-off commands (python -m scripts.<name>). They are not imported by the API.
Cross-module data: if several modules read the same records, those models live in one shared package (for example app/domain/). Modules filter and interpret those records. They do not copy the tables into their own models.py.

Frontend rules
One URL, one route folder. page.tsx is the shell: title, layout, and server data for that screen. Interactive pieces live in a sibling file (<screen>-client.tsx, <screen>-table.tsx) with a clear name. A page file does not contain every table, form, and dialog for the product.

app/(app)/<area>/<screen>/
  page.tsx
  <screen>-client.tsx
components/ui/            # visual primitives, no business calls
components/<feature>/     # used by two or more screens
lib/api/client.ts         # browser calls
lib/api/server.ts         # server-side calls
lib/api/types.ts          # response types
lib/<topic>.ts            # pure functions (format, math)
hooks/                    # stateful hooks used in two or more places
Screens call lib/api. They do not open fetch with a handwritten URL.
A component used by one screen stays next to that screen. Move it to components/ only on the second use.
components/ui has no knowledge of routes or endpoints.
Static copy and option lists go in data/ or next to the screen, not inside a shared button component.
How to add a feature
Name the capability. Create app/modules/<name>/ and the route folder. Do not extend an unrelated module because its file is already open.
Add the route in schemas.py and router.py, the rule in service.py, and the table change in models.py plus a migration.
Mount the router from main.py in one line.
Add the screen as its own route folder and call the new endpoint through lib/api.
Put tests in tests/modules/test_<name>.py (or a matching package). Test the service rule directly. Do not only test through the UI.
Refuse these shapes
A utils.py or helpers.py that accumulates unrelated functions. Name the file by the job (pagination.py, money_format.py).
A router that contains the business rules.
A React page that fetches, maps, and renders every entity in the product.
A new endpoint pasted into an existing module because that module was created first.
Background work done inside the request.
A third-party payload parsed in the service. Parse it in that integration's file and return a plain structure.
Generated files that restate the same type in five places. One schema on the server, one type on the client.
